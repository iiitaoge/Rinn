  #2 对，但再追一步

  发出方不知接收方 = 解耦。这个属性本身不是目的，它换来的是扩展性。

  ▎ 当"加税" event 被 publish，谁来响应？AppraisalSystem 改 
  ▎ anger/anxiety、KnowledgePropagation 让听到的人记住这件事、DecisionSystem 
  ▎ 重算 utility，未来可能还有 LogSystem。

  如果 publisher 要知道每个 subscriber，加新 subscriber 就改
  publisher。解耦让你单向加新订阅者——和你 ECS 加 System
  那种"不动旧代码"是同款扩展性。这条你直觉对的，往下走。

  #1 部分对，但你还在 pull 心智里

  你说"系统检测事件变化，需要一个监测信号"——这描述的是轮询（polling），仍然是
  frame-driven 的延伸。System 主动去看"有事吗？"

  event-driven 真正的换轨是 push，不是 
  pull。事件不是被"检测到"的，是被"送上门"的。

  引导问题：

  ▎ EmotionDecaySystem 每帧做的是 for entity in pool: intensity *= 
  ▎ decay——它主动扫一遍 pool。
  ▎
  ▎ 现在 AppraisalSystem 要响应"加税" 
  ▎ event。如果它每帧扫一个"事件池"看有没有新事件，那本质上还是 pull——只是把扫 
  ▎ pool 换成扫事件池。
  ▎
  ▎ 不轮询的话，AppraisalSystem 怎么知道事件来了？谁负责告诉它？

  这个问题想清楚，你就摸到 EventBus 的核心 API 了——它需要一个动作，是
  EmotionDecaySystem 那种纯被动 System 不该有的。

  #3 答反了，这是三道里最重要的

  "时序可能不太重要，实在不行用事件类型分类"——危险信号。事件类型分类（信息/物质
  ）解决的是 what，不是 when。两件事正交。

  走一遍这个场景：

  ▎ 同一帧，村民甲被两个事件影响：
  ▎ - EventA = {type: "priest_died"} → AppraisalSystem 给他 +loneliness
  ▎ - EventB = {type: "heard_priest_last_words"} → AppraisalSystem 给他 +faith 
  ▎ satisfaction
  ▎
  ▎ 两个 event 同帧到达，subscriber 都是 AppraisalSystem。
  ▎
  ▎ Q1：A 先处理还是 B 先处理？谁定？
  ▎ Q2：如果"任意顺序"——同样输入跑两次，村民甲最终情绪可能不一样吗？
  ▎ Q3：如果不一样——这是个确定性系统还是非确定性系统？非确定性的系统怎么调试？

  再加一个更扎实的：

  ▎ AppraisalSystem 处理 EventA 给村民甲 +loneliness 
  ▎ 时，这个加法触发阈值，让他当场 publish EventC = {type: "broke_down"}。
  ▎
  ▎ EventC 什么时候被处理？三种方案：
  ▎
  ▎ (a) 当场立刻处理——深递归，可能死循环，难调试
  ▎ (b) 当帧但排到队尾——本帧之内一直 drain 到队列空
  ▎ (c) 下一帧处理——引入 1 帧延迟，多事件链反应要多帧传播完
  ▎
  ▎ 三种代价各是什么？哪个对应 chat log 1968 那句"这一帧的 event 
  ▎ 是不是要下一帧才被消费"？

  这两个场景全是 EventBus 设计必须先回答的问题，不是"实在不行再说"。

  frame-driven 下时间是连续的——dt 一推大家都推，谁先谁后无所谓，最后状态一样。
  event-driven 下时间是离散且有顺序的——顺序不定 = 行为不定 = 非确定性 = 涌现
  bug。chat log 1939 那句"AI bug 延迟可见、难复现"，根源全在这里。
