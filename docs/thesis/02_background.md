# 第 2 章 相关技术与理论基础

本章对支撑 Project Rinn 引擎设计与实现的关键技术与理论作集中梳理，包括实体-组件-系统架构、面向数据设计与缓存局部性、Lua 嵌入式脚本与 sol2 绑定、raylib 渲染管线与 OpenGL 基础，以及 HD-2D 视觉风格的技术构成。后续章节中所讨论的具体设计决策都可以追溯到本章所列的某一项理论或工程惯例。

## 2.1 实体-组件-系统架构

### 2.1.1 从面向对象到组合的范式迁移

传统面向对象设计在游戏对象体系中的早期实践，往往采用一棵深度较大的继承树：从 `GameObject` 派生出 `Pawn` 与 `Item`，再从 `Pawn` 派生出 `Player` 与 `Enemy`，依此类推。当游戏内容扩张时，这种结构会面临两类典型困境。其一是"菱形继承"：当 `FlyingEnemy` 既要继承 `Enemy` 又要继承 `Flyable` 时，C++ 多重继承所带来的虚基类、内存布局复杂度与歧义解析，会让代码迅速失控。其二是"层级僵化"：一旦设计师希望某个 `Item` 临时获得移动能力（例如可被推动的箱子），就需要在继承树中插入新节点或反复重构。

组合（composition）思想给出了另一条路径：把"是什么"拆解为一组可插拔的属性，把"怎么做"实现为针对某一组属性的纯函数。游戏对象不再通过派生区分类型，而是通过持有不同的组件子集来体现差异。Robert Nystrom 在 *Game Programming Patterns* 一书中将这一模式称为 *Component pattern*，并指出其本质是"组合优于继承"在游戏对象建模上的应用。

### 2.1.2 ECS 三要素与典型工业实践

ECS 是组合思想的极端化产物。其三要素分别是：

- **Entity（实体）**：通常以一个轻量整数标识符表示，本身不携带任何业务数据，只作为组件的"标签"存在。
- **Component（组件）**：纯数据结构，描述实体的某一项属性（位置、速度、纹理、碰撞盒等）。组件之间不互相引用业务行为。
- **System（系统）**：纯函数，按"我关心哪些组件类型的组合"声明输入，对所有同时持有这些组件的实体执行统一的处理。

这一抽象的关键收益在于：组件按类型聚集存储于连续内存中，系统对其进行线性遍历，自然形成"数据并行"的执行模式，CPU 缓存与流水线得以充分利用。EnTT 是 C++ 生态中影响最广的开源 ECS 库，其文档与源代码对 sparse set、view、group 等概念给出了完整定义；Bevy 在 Rust 生态中以"插件 + 调度器"风格构建了整套引擎；Unity 自 2018 年推出的 DOTS 将 ECS、Job System 与 Burst 编译器三者打包，使主流商业引擎首次原生支持面向数据范式。Bitsquid 团队在其早期博客中也从工程实践角度，详细讨论了如何用关系数据库式的"实体表 + 组件表"组织数据。

### 2.1.3 ECS 与 Component-Based / Actor 模型的差异

ECS 经常与 Component-Based（CB）模式与 Actor 模型混用，但三者并不等同。CB 模式典型如 Unity 早期的 `MonoBehaviour`，组件本身既包含数据也包含行为，且通常以指针挂载在 GameObject 之下，内存布局并不强调"按类型聚集"。Actor 模型如 Unreal Engine 的 `Actor`，则将逻辑与生命周期高度封装在对象内部，组件只是其装饰品。相比之下，ECS 强调"数据归数据、行为归系统"的彻底分离，并对组件存储的连续性提出明确要求，这是其性能优势的根源。

## 2.2 面向数据设计与缓存局部性

### 2.2.1 现代 CPU 的缓存层级与延迟

现代 x86-64 处理器的内存子系统通常包含三级缓存：每核心独占的 L1 数据缓存（典型 32 KB，访问延迟约 4–5 cycles）、每核心独占或与超线程共享的 L2 缓存（典型 256 KB–1 MB，约 12 cycles）、跨核心共享的 L3 缓存（典型数 MB 至数十 MB，约 40 cycles），以及主存（约 200–300 cycles）。L1 与 L2 之间的延迟差距已达到接近一个数量级，L3 与主存之间则更甚。Drepper 在 *What Every Programmer Should Know About Memory* 中系统阐述了这一层级的工作原理：缓存以固定大小（典型 64 字节）的"缓存行"为最小传输单元，命中与否在很大程度上决定了热循环的真实性能。

由此衍生出两条工程经验：其一，**让经常一起访问的数据彼此靠近**（空间局部性）；其二，**让最近访问过的数据有机会被复用**（时间局部性）。游戏循环中的 System 往往对大量同类组件做线性扫描，因而对空间局部性极度敏感。

### 2.2.2 AoS 与 SoA：两种数据布局的取舍

考虑物理系统对位置与速度的更新，每个实体需要 `(x, y, vx, vy)` 四个浮点数。

**AoS（Array of Structures）**布局将每个实体的字段聚合在同一结构体内，再用数组容纳所有实体：

```cpp
struct Entity { float x, y, vx, vy; };
std::vector<Entity> entities;
```

这种布局贴合"一个实体的所有字段一起读取"的直觉，但当系统只关心 `x` 与 `y`、不关心 `vx` 与 `vy` 时，每条缓存行会被未使用的字段"稀释"。

**SoA（Structure of Arrays）**布局将同名字段聚集为独立数组：

```cpp
struct Entities { std::vector<float> x, y, vx, vy; };
```

只读 `x` 时，整条缓存行都是 `x` 数据，缓存利用率最大化，并天然适合 SIMD 向量化（如 AVX2 一次处理 8 个 `float`）。其代价是"每实体所有字段一起处理"时需要并行索引多个数组，编程稍显繁琐。

ECS 的 SparseSet 采取的是介于二者之间的"按组件类型分桶"策略：每种组件类型独立持有一个稠密数组，相当于在组件粒度上实现了 SoA。

### 2.2.3 SparseSet 的双数组结构

SparseSet 是 ECS 中应用最广的组件存储数据结构，由两个数组组成：

- **Sparse 数组**：以实体索引为下标，长度为最大实体数；存储该实体在 Dense 数组中的位置，未持有该组件时为哨兵值。
- **Dense 数组**：连续存储所有实际持有该组件的数据，长度等于活跃组件数。

借助 Sparse → Dense 的两次间接寻址，可在 O(1) 时间内完成 has / get / emplace / remove 四种核心操作；对 Dense 数组的线性遍历则保留了缓存友好的特性。当需要删除中间元素时，采用"swap-and-pop"惯用法将队尾元素填补空位，即可避免移动大量数据。

### 2.2.4 软件预取与 Pointer Chase

即便 SparseSet 已经做到 O(1) 寻址，"先读 Sparse，再读 Dense"的两步操作仍构成所谓 *pointer chase*：第二次读取的地址依赖于第一次读取的结果，因而无法被乱序执行单元提前发出。当 Sparse 与 Dense 都不在 L1 中时，每次 get 都可能等待两次 memory load。x86 平台提供 `_mm_prefetch` 指令族，允许程序员主动告知 CPU "请提前把这条缓存行拉入 Lx"。在已知的访问模式（例如顺序遍历 dense 数组）下，提前若干步预取下一条数据，可将原本串行的两次 load 转化为流水线并行，从而显著降低有效延迟。

## 2.3 Lua 嵌入式脚本与 sol2 绑定

### 2.3.1 数据-逻辑分离的工程价值

游戏的"机制"通常由 C++ 等编译型语言实现，以追求性能与稳定；游戏的"内容"——关卡布局、对话脚本、敌人配置、平衡数值——则需要频繁修改与迭代，重新编译 C++ 的成本难以接受。将这部分内容外置为脚本或数据文件，是行业的通行做法。脚本语言通常具备运行时加载、热更新、易于学习等优点，能够承担"策略层"的职责。

### 2.3.2 Lua 5.4 的设计特点

Lua 由 PUC-Rio 的 Roberto Ierusalimschy 等人于 1993 年发布，是一门轻量级、原型继承式的多范式脚本语言。其核心解释器源代码不足两万行，编译后的运行时通常仅需数百 KB，配以 MIT 许可证与可重入设计，使其极其适合嵌入到宿主应用程序中。Lua 5.4 引入了世代式垃圾回收、整数子类型、to-be-closed 变量等现代特性，进一步提升了在游戏场景中的可用性。Lua 在游戏行业的应用极为广泛，包括《魔兽世界》客户端 UI、《愤怒的小鸟》关卡逻辑、Roblox 客户端等。

### 2.3.3 sol2：基于 C++17 模板元编程的双向绑定

C++ 与 Lua 之间的绑定历经了从手写 C API、LuaBind、tolua++ 到 sol2 的演进。sol2 由 ThePhD（Jeremy Ong）等人开发，是一个仅头文件、无外部依赖、利用 C++17 模板元编程能力的现代绑定库。其核心抽象包括：

- `sol::state`：封装 `lua_State*`，并提供 RAII 生命周期管理。
- `set_function`：将 C++ 任意可调用对象（普通函数、lambda、成员函数、`std::function`）注册为 Lua 全局函数，模板系统自动推导参数与返回值的类型转换。
- `new_usertype`：将 C++ 类型导出给 Lua，可选择性地暴露字段、方法与构造函数。
- `sol::table`：表示 Lua table，支持 `t.get<T>(key)` 与 `t.set(key, value)` 的类型安全访问。

借助 sol2，C++ 与 Lua 的双向调用代码量可较手写 C API 减少一个数量级以上，且类型错误能够在编译期或第一次运行时被显式抛出，对提升脚本子系统的工程可维护性意义重大。

## 2.4 raylib 渲染管线与 OpenGL 基础

### 2.4.1 raylib 与 rlgl 抽象层

raylib 是一个由 Ramon Santamaria 维护的轻量级 C 语言游戏开发库，遵循 zlib 许可证，专为教学与小型项目设计。其设计哲学强调"无依赖、易上手"，将 OpenGL、音频、输入、字体等模块封装为风格统一的 C API。在其核心之上，raylib 自带的 `rlgl` 模块提供了一层介于"高层 raylib API"与"原生 OpenGL"之间的中间抽象，允许用户通过 `rlBegin / rlVertex3f / rlTexCoord2f / rlEnd` 这类立即模式 API 直接提交三角形与四边形，特别适合在已有引擎之上插入自定义绘制路径。Project Rinn 的精灵 3D 化绘制即基于 rlgl 实现。

### 2.4.2 顶点着色器与片段着色器

OpenGL 3.3+ 的可编程渲染管线由若干 shader 阶段串联：

- **顶点着色器**（vertex shader）：对每个输入顶点执行，主要任务是将顶点坐标从模型空间通过 MVP 矩阵变换到裁剪空间，并向后续阶段输出与位置关联的属性（纹理坐标、颜色、法线等）。
- **片段着色器**（fragment shader）：对光栅化后的每个像素执行，决定该像素的最终颜色，可采样纹理、计算光照、做后处理等。

二者通过 `in / out` 关键字在 GLSL 中显式声明输入输出，CPU 侧通过 `uniform` 变量传入每帧或每物体一致的参数（如光源方向、纹理槽、自定义法线向量）。

### 2.4.3 Camera3D 与 2.5D 场景

raylib 的 `Camera3D` 结构封装了相机位置、目标点、上方向、视场角与投影类型（透视或正交）。当将像素美术放置在透视相机之下、并统一以世界 Y 轴为"高度"方向时，便可获得一种介于纯 2D 与纯 3D 之间的"2.5D"视觉效果——这是 HD-2D 风格的几何基础。Project Rinn 选择了 60° 俯视的透视相机配置，并通过约束相机仅在 XZ 平面平移、保持俯角不变，避免了完整 3D 场景所需的复杂控制。

## 2.5 HD-2D 视觉风格综述

### 2.5.1 风格构成

HD-2D 的视觉冲击力来自多种渲染要素的叠加，其要素可粗略归纳为四组：

1. **几何层**：2D 像素美术的角色与瓦片在透视相机下被赋予空间感。
2. **光照层**：方向光 + 自发光 + 体积光，使得像素角色出现明暗与立体感，地面则保留较为平整的烘焙效果。
3. **后处理层**：bloom 提取高亮区域并模糊扩散，营造"闪光"质感；tilt-shift 通过对画面上下区域施加景深模糊模拟微缩模型镜头效果；色彩校正与暗角进一步统一画面调性。
4. **细节层**：粒子（飞舞的尘埃、火焰、水雾）、屏幕空间反射、阴影投射等。

### 2.5.2 关键技术点

从渲染技术角度，实现 HD-2D 的核心难点包括：

- **法线贴图与精灵光照**：传统 2D 精灵不携带法线信息，因此无法参与基于光照模型的明暗计算；HD-2D 通过为像素精灵手绘或自动生成法线贴图，使其能够参与朗伯或 Phong 模型，从而呈现"被光照亮"的立体感。
- **深度排序与 Z-buffer 修正**：当 2D 精灵被放入 3D 场景时，简单的画家算法可能与硬件深度测试冲突；常见做法是按 `(layer, y_bottom)` 等键先行排序，或对精灵的几何高度做特殊处理以获得正确的遮挡关系。
- **后处理管线**：bloom、tilt-shift、色彩调色等通常基于 framebuffer 后处理实现，需要引擎支持渲染目标切换。
- **风格一致性**：像素美术与现代后处理的混搭必须把握分寸，过度后处理会破坏像素美感，因此调色与强度需要美术与程序紧密协作。

### 2.5.3 公开技术资料

Square Enix 在 GDC 与 CEDEC 的演讲中分享了《八方旅人 2》在 HD-2D 上的若干技术细节，包括法线贴图、光体积、tilt-shift 实现要点；社区方面，Godot 与 Unity 论坛上出现了大量 HD-2D 风格的实现教程与开源插件。然而，针对自研 C++ 引擎的、面向教学的完整开源参考实现仍然较少，这亦构成本课题在第 7 章进行原理验证的现实意义。
