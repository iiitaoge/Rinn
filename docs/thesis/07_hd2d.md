# 第 7 章 HD-2D 渲染原理验证

HD-2D 是本课题在视觉风格上的目标。受限于毕业设计的时间窗口，本章不追求完整的 HD-2D 后处理管线，而是聚焦于最核心的"使 2D 精灵在 3D 场景中获得明暗体积感"这一原理：通过区分立式精灵与地面瓦片的几何朝向、为它们赋予不同的法线、在片段着色器中以朗伯模型计算光照，得到"一明一暗"的初步效果。完整的 bloom、tilt-shift、体积光等后处理被列入第 9 章的展望。

## 7.1 HD-2D 风格的视觉构成

HD-2D 风格的视觉冲击力并非来自单一渲染技术，而是若干要素的精心叠加。归纳起来，可以将其拆解为四个"层"：

**几何层**——像素美术的角色与瓦片放置在透视相机之下，为画面赋予空间深度。这一层意味着引擎必须具备 3D 场景能力，至少需要透视相机、深度测试与世界坐标系；不再像传统 2D 那样所有元素都位于屏幕空间。

**光照层**——一个或多个方向光、点光源与自发光物体使 2D 精灵呈现明暗变化，使地面有"被照亮"的感觉。这是 HD-2D 区别于普通像素艺术的最显著特征：传统像素美术的明暗依靠美术手绘，HD-2D 的明暗则部分由实时光照计算。

**后处理层**——bloom 提取高亮区域并模糊扩散，使像素角色的高光部位"发光"；tilt-shift 通过对画面上下区域施加可变景深模糊，模拟微缩模型镜头效果；色彩校正与暗角统一画面调性。这一层的效果通常在屏幕空间（Framebuffer）完成，不直接修改场景几何。

**细节层**——粒子（飞舞的尘埃、火焰、水雾）、体积光、屏幕空间反射、阴影投射、动态雾等。这一层的内容因游戏而异，但都依赖前三层提供的基础设施。

Project Rinn 当前的"原理验证"聚焦于几何层与光照层中最基础的部分：透视相机已经在第 5 章 RenderSystem 中实现；本章重点说明如何为 2D 精灵分配法线，使它们能够进入光照计算。

## 7.2 立式精灵与地面瓦片的几何区分

要让光照对 2D 精灵生效，首先需要明确"哪些精灵是立着的、哪些是平铺的"。这是一个几何问题，不是渲染问题——立式精灵（角色、树木、栏杆等）的"正面"应当朝向相机或光源，地面瓦片（草地、石板、河流等）的"正面"应当朝上。

### 7.2.1 Sprite 组件的扩展

`Sprite` 组件中加入了一个布尔字段 `is_ground`：

```cpp
struct Sprite {
    size_t texture_id;
    size_t normal_id = 0;
    float  width, height;
    float  src_x = 0, src_y = 0, src_w = 0, src_h = 0;
    bool   is_ground = false;
};
```

这是用最小代价区分两种语义的方式：默认值 `false` 表示立式精灵；只有在地面瓦片场景下（典型由 `map_loader.lua` 处理图块层时）才显式置为 `true`。`is_aggregate_v` 与 `is_trivially_copyable_v` 两条编译期约束因此仍然成立，组件依旧可以被零拷贝传递与序列化。

### 7.2.2 顶点摆放：XZ 平面 vs XY 立面

`DrawSprite3D` 函数根据 `ground` 标志选择两种不同的顶点摆放方式：

```cpp
if (ground) {
    // 水平铺在 XZ 平面，pos 是角落坐标
    rlTexCoord2f(u1, v1); rlVertex3f(pos.x,            pos.y, pos.z);
    rlTexCoord2f(u1, v2); rlVertex3f(pos.x,            pos.y, pos.z + size.y);
    rlTexCoord2f(u2, v2); rlVertex3f(pos.x + size.x,   pos.y, pos.z + size.y);
    rlTexCoord2f(u2, v1); rlVertex3f(pos.x + size.x,   pos.y, pos.z);
} else {
    // 竖直站立，X 方向居中
    float hw = size.x / 2.0f;
    rlTexCoord2f(u1, v2); rlVertex3f(pos.x - hw,       pos.y, pos.z);
    rlTexCoord2f(u2, v2); rlVertex3f(pos.x + hw,       pos.y, pos.z);
    rlTexCoord2f(u2, v1); rlVertex3f(pos.x + hw,       pos.y + size.y, pos.z);
    rlTexCoord2f(u1, v1); rlVertex3f(pos.x - hw,       pos.y + size.y, pos.z);
}
```

地面瓦片：四个顶点共享同一 Y 坐标（`pos.y`），分布在 XZ 平面上，构成一片水平面，等价于"贴在地上的纸片"。
立式精灵：四个顶点共享同一 Z 坐标（`pos.z`），分布在 XY 立面上，X 方向以 `pos.x` 为中心居中、Y 方向向上延展，构成一片"立在地上的纸片"。

四个顶点的提交顺序遵循逆时针，这一顺序对法线方向至关重要——OpenGL 默认按右手定则，从顶点排列推算"前面"指向相机外侧。Project Rinn 的两种摆放分别使地面正面朝上（+Y）、立式正面朝相机（+Z），与下一节的 shader 法线设定相吻合。

### 7.2.3 两趟渲染与法线切换

如第 5 章 5.1.5 节所述，`DrawSprites` 将地面瓦片与立式精灵分两趟提交，并在两趟之间切换 shader 中的 `facenormal` uniform：

```cpp
facenormal = tile_normal;       // (0, 1, 0)
Facenormal();                   // SetShaderValue → uniform vec3 facenormal
for (Entity e : ground_tiles) DrawSprite3D(..., true);

facenormal = vertical_normal;   // (0, 0, 1)
Facenormal();
std::sort(sprites.begin(), sprites.end(), /*…按 y_bottom 排序…*/);
for (Entity e : sprites) DrawSprite3D(..., false);
```

`facenormal` 变量在 C++ 端表达"本批次精灵的整体朝向"，并通过 uniform 一次性下发到 GPU 而非随顶点逐个传递。这是当前阶段最低成本的实现方式：所有立式精灵共享一个法线方向（朝相机），所有地面瓦片共享一个法线方向（朝上）。代价是无法表达"侧向"或"倾斜"的精灵，未来若引入旋转角色或斜坡，需要把法线放回到顶点属性。

## 7.3 Shader：法线贴图与朗伯光照

引擎当前使用一对最小可运行的着色器（`assets/shaders/test.vs` 与 `test.fs`）来实现"基于法线的明暗"。

### 7.3.1 顶点着色器

顶点 shader 的职责仅限于把顶点从模型空间通过 MVP 矩阵变换到裁剪空间，并把纹理坐标与颜色透传给片段 shader：

```glsl
#version 330
in vec3 vertexPosition;
in vec2 vertexTexCoord;
in vec4 vertexColor;
uniform mat4 mvp;
out vec2 fragTexCoord;
out vec4 fragColor;
void main() {
    fragTexCoord = vertexTexCoord;
    fragColor    = vertexColor;
    gl_Position  = mvp * vec4(vertexPosition, 1.0);
}
```

这与 raylib 自带的默认 shader 几乎一致，确保所有 raylib 风格的顶点提交都能正确工作。

### 7.3.2 片段着色器：法线贴图采样 + 朗伯光照

片段 shader 是本章的核心：

```glsl
#version 330
in vec2 fragTexCoord;
in vec4 fragColor;
uniform sampler2D texture0;
uniform vec3      facenormal;
uniform sampler2D sprite_normal;
vec3 lightDir = vec3(1, 0, 1);
out vec4 finalColor;
void main() {
    vec4 texel  = texture(texture0,       fragTexCoord);
    vec4 norel  = texture(sprite_normal,  fragTexCoord);
    vec3 normal = norel.rgb;
    vec3 N      = normal * 2.0 - 1.0;          // [0,1] → [-1,1]
    vec3 L      = normalize(lightDir);
    float NdotL = max(dot(N, L), 0.0);
    finalColor  = vec4(texel.rgb * NdotL, texel.a);
}
```

逐步解释：

1. `texture0` 是 raylib 在 `rlSetTexture` 后绑定的 albedo（基础色）纹理；`sprite_normal` 是引擎在 `DrawSprite3D` 中通过 `SetShaderValueTexture` 绑定的法线贴图。两者共享同一 UV `fragTexCoord`，通常由美术为同一精灵分别绘制 albedo.png 与 albedo_n.png。
2. 法线贴图按行业惯例以 `[0, 1]` 编码法线分量；shader 中通过 `normal * 2.0 - 1.0` 解码回 `[-1, 1]` 的标准向量空间。
3. `lightDir = vec3(1, 0, 1)` 暂时硬编码——这是当前实现的局限之一，未来应当声明为 uniform 以便在 C++ 与编辑器侧调节。
4. `dot(N, L)` 给出朗伯模型下的"漫反射强度"，再以 `max(..., 0.0)` 截掉负值（即面向背离光源的部分），最后乘以 albedo 得到最终颜色。alpha 通道直接透传以支持半透明。

注释行 `//finalColor = vec4(N * 0.5 + 0.5, 1.0);` 是开发期常用的"法线可视化"调试输出，反映了开发过程中"把抽象的法线向量映射回 RGB 颜色"的诊断技巧。

### 7.3.3 facenormal uniform 与 sprite_normal 的关系

值得指出的是，当前 shader 实际只使用了 `sprite_normal` 采样得到的法线，而 `facenormal` uniform 暂未被参与最终计算。这反映了引擎当前正处于从"统一面法线"过渡到"逐像素法线"的中间阶段：早期版本仅用 `facenormal` 控制整片精灵的朝向，配合简单的明暗分层；后引入法线贴图以追求更细腻的光照效果，于是 `sprite_normal` 取代了 `facenormal` 在像素层面的角色，但 `facenormal` 保留为 uniform，用于未来可能的"按整批精灵切换光照模式"的扩展。

## 7.4 当前局限与改进方向

本章所完成的工作只是 HD-2D 渲染的"原理验证"，明确将以下不足列出，并对应到第 9 章的展望，避免读者对当前实现的能力产生过高期望。

**光照参数硬编码**。`lightDir` 直接写死于 shader 源码中，无法在 C++ 或编辑器端调整。修复方式是在 shader 中声明 `uniform vec3 lightDir;`，C++ 端在 `RenderSystem::Init` 时缓存其 location，每帧或每场景调用 `SetShaderValue` 推送当前光源方向。这是一个 30 分钟以内即可完成的小改动。

**单光源模型**。当前仅一个方向光，无环境光、无点光源、无阴影。HD-2D 风格的"温暖咖啡馆灯笼"等典型场景需要支持多光源。改进路径是在 shader 中循环若干 uniform 数组，或引入延迟着色（deferred shading）框架。后者代价较大，建议在引入编辑器、能可视化布光之后再实施。

**未做 gamma 校正与 sRGB 处理**。当前所有颜色计算在 sRGB 空间下进行，与物理正确的线性空间光照计算存在偏差，导致明暗对比偏暗、过渡不平滑。修复方式是 framebuffer 切换到线性 sRGB 模式、shader 输入做 `pow(srgb, 2.2)` 解码、输出做 `pow(linear, 1/2.2)` 编码。

**法线非真法线**。立式精灵的法线统一为 `(0, 0, 1)`，意味着所有立式精灵都朝向同一方向，无法表达侧身、转身或倾斜。完整解决需为每个精灵实例传递独立的旋转向量，并在 shader 中将法线贴图采样结果与该向量做切线空间变换。

**深度排序与 Z-buffer**。当前对立式精灵使用画家算法（按 `(layer, y_bottom)` 排序绘制），对地面层不排序。这种简化在 demo 规模下有效，但当透视角度变化或遮挡关系复杂时容易出错。HD-2D 严肃实现需要每个精灵根据其几何位置参与硬件深度测试，并配合特殊的"立式 billboard 投影修正"以避免精灵浮空或穿地。

**缺失后处理管线**。bloom、tilt-shift 景深、色彩调色、暗角等后处理目前完全缺失。这是 HD-2D 视觉特征中最具辨识度的一组要素，也是后续工作的"短期高收益"项。实现需要支持渲染目标（RenderTexture）切换、屏幕空间高斯模糊、亮度阈值提取等基础设施，估计工作量约一周到两周。

**缺失粒子与体积光**。粒子系统与体积光是制造氛围的关键，但都需要在 ECS 之上新增子系统（粒子组件 + 粒子更新系统 + 屏幕空间体积光后处理）。建议在编辑器与后处理完成之后再行引入。

第 9 章展望部分将上述短板按"短期、中期、远期"重新组织，并给出明确的优先级与预估工作量。本章到此为止，已经完成对当前 HD-2D 实现"做到了什么、没做到什么"的诚实交代。
