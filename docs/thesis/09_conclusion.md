# 第 9 章 总结与展望

## 9.1 工作总结

本课题以"自下而上"的方式设计并实现了一款基于实体-组件-系统架构的轻量级游戏引擎 Project Rinn，并在其上完成了 HD-2D 渲染风格的原理验证。围绕"以教学与可拓展性为优先"的目标，全部源码以 C++20 与 raylib 5.5 为基础，配合 Lua 5.4 + sol2 的脚本绑定、Dear ImGui + rlImGui 的调试支持，以及 GoogleTest 的单元测试框架，形成一个可读、可调、可演化的样本。

完成的工作可归纳为六个层面。**核心层**自主实现了 ECS 的全部基础设施：32 位整数承载的 Entity 句柄通过版本号防御 ABA 问题；环形缓冲实现的 EntityPool 提供 O(1) 索引复用；SparseSet 双数组结构兼顾 O(1) 增删与稠密线性遍历，并提供两阶段软件预取接口；模板特化与原子计数器在编译期为每种组件分配唯一 8 位 ID；Registry 借助签名位图与组件池数组提供"实体维度"与"组件维度"的双向访问；多组件 View 采用最小池驱动算法，并通过构造期缓存彻底消除热循环中的虚函数。**子系统层**实现了渲染（含 3D 相机、精灵 3D 化、中文字体、对话气泡）、纯位置积分的物理、空间哈希加 AABB 的二阶段碰撞、薄封装的输入、单 BGM 流的音频、基于 Dear ImGui 的实体检视器六个子系统，覆盖了一个 2D 游戏的最小可运行能力集合。**资源与脚本层**提供 ID 化的纹理管理与基于 sol2 的双向绑定，使关卡布局、对话、场景演化全部可由 Lua 描述；通过 Tiled 编辑器导出的 Lua 数据自动构造 ECS 实体，将美术与策划纳入工作流。**HD-2D 层**通过区分立式精灵与地面瓦片的几何朝向、为它们绑定不同的法线、在片段着色器中进行朗伯光照计算，得到了"一明一暗"的初步体积感。**NPC AI 层**实现了完整的需求-情绪-决策-执行管线：EventBus 以确定性 FIFO 传递世界事件；AppraisalSystem 将事件映射为主观化情绪 delta 并通过 bitset 实现信息差；DecisionSystem 以 Utility AI 三因子公式（效用 = 增益 × 需求紧迫度 × 情绪调制因子）驱动 NPC 自主选择行动；ActionExecutionSystem 在动作完成时发布新事件形成涌现叙事循环；LineSystem 的 Agency-Aware 过滤机制确保台词与角色立场一致；四 NPC 端到端场景在"加税令"剧情下验证了群体自发行为与信息不对称响应。**测试层**以 70 余条 GoogleTest 用例覆盖了 ECS 核心的接口语义与边界行为；以独立运行的 cache miss 与 false sharing 基准定量验证了数据布局的实际收益。

主要技术贡献可概括为如下五点：（1）一套完整、可读、自带性能基准的 ECS 核心实现，可作为教学与同类项目的参考样本；（2）以"机制 / 策略"边界划分为核心思想的脚本绑定方案，使 C++ 与 Lua 的协作既高效又清晰；（3）数据驱动的 Tiled 地图加载与对话分支系统，将关卡设计与剧情迭代权交还给非程序员；（4）基于 Utility AI 与情绪-需求双层状态的 NPC AI 管线，在 ECS 框架内实现了可扩展、可调试、可 Lua 配置的自主角色行为；（5）面向后续扩展明确预留章节位置与代码插入点的工程组织方式，为编辑器等未来模块的引入消除结构性阻力。

## 9.2 不足之处

诚实评估当前实现，仍有若干工程债务与设计妥协需要在后续工作中处理。

**命名空间级全局造成的隐式单例**。`RenderSystem`、`AudioSystem`、`CollisionSystem` 等子系统通过命名空间内的 `inline` 全局变量承载状态，使得 API 极薄、调用方便，但代价是无法在同一进程内持有第二份相机、第二个音频上下文或第二份碰撞网格。一旦未来需要 RenderTexture、多场景或多线程，这一选择就会成为障碍。修复路径是将每个子系统重构为类，并在合适的层级（Engine 或 Application）持有其实例。`AudioSystem.hpp` 的命名空间 `static` 全局还存在跨翻译单元状态分裂的潜在风险，应优先改为 `inline`。

**Lua 字符串调度的扩展性瓶颈**。`LuaBinder::set / remove` 通过对组件名做字符串比较来分发，新增组件需要在两处同时追加 `else if` 且字段名硬编码。这种模式在组件类型较少时尚可接受，但随着引擎演化将不可持续。改进方向是引入"组件元描述"机制：以 sol2 的 `new_usertype` 暴露强类型组件、或以代码生成方式从单一组件清单生成绑定。

**HD-2D 仅完成原理验证**。第 7 章已经诚实列出了光照硬编码、单光源模型、无 gamma 校正、立式精灵法线非真法线、无 Z-buffer 深度修正、缺失 bloom / tilt-shift / 体积光等局限。这些局限不影响"原理是否成立"的回答，但与"完整 HD-2D 风格"之间仍有可观距离。

**System 调度硬编码于 main.cpp**。当前每帧执行哪些 System、按什么顺序，全部以函数调用顺序写在 `main.cpp` 的 while 循环中。未来若需要多场景、暂停 / 单步、Editor 模式禁用某些 System，就需要把调度抽象为可配置的 Schedule，类似 Bevy 的 stage 系统。这是引擎从"写死的脚本"到"可编程的调度器"演进的关键一步。

**资源路径硬编码与跨工作目录的脆弱性**。`main.cpp` 与多个 Lua 脚本均直接使用 `"../../../assets/..."` 这样的相对路径，强依赖运行时工作目录恰好是 `build/Debug`。改进路径是在启动时使用 `std::filesystem` 自动定位项目根目录，或在 CMake `POST_BUILD` 中将 assets 复制到 exe 同目录，路径恒为 `assets/...`。

此外还有若干风格层面的小问题：命名风格混用（PascalCase / snake_case / camelCase 交替出现）、`#include "iostream"` 等用引号包含标准库、`[[nodiscard]]` 用于 emplace 等不必丢弃返回值的接口、SparseSet `emplace` "重复返回旧值"语义在 LuaBinder 中需要"先 remove 再 emplace"的两步样板等。这些问题已在 `docs/audit/Project_Audit.md` 中做了详细记录与分级，可作为后续清理的工程清单。

## 9.3 未来工作

后续工作按预期投入与收益分为短期、中期、远期三档。这一分级与引擎当前的章节结构一一对应——任意一档完成后，可直接将对应内容从"展望"提级为正式章节，插入第 7 章 HD-2D 与第 8 章性能测试之间，前 7 章无需任何重排。

### 9.3.1 短期工作：HD-2D 渲染的完善（数周）

短期工作以"在不引入新子系统的前提下，让 HD-2D 视觉效果更接近成品"为目标。具体计划包括：

1. 引入多光源支持：扩展 `light_color` / `ambient_color` 机制，在 shader 中循环若干 `uniform Light lights[N]` 数组，支持环境光 + 方向光 + 一两个点光源；
2. 启用 sRGB framebuffer 与 gamma 校正，让明暗过渡更接近真实；
3. 在精灵渲染路径上引入按 `y_bottom` 投影到 Z 的微调，使硬件深度测试与画家算法配合得到正确的遮挡关系；
4. 引入屏幕空间后处理框架：以 RenderTexture 作为离屏目标、以两 pass 高斯模糊实现 bloom、以可调强度的 tilt-shift 与暗角统一画面调性；
5. 同步在 RenderSystem 中预投影排序键、复用容器内存，消除第 8 章指出的两条已知瓶颈。

预计完成上述工作后，第 7 章可由"原理验证"升级为"完整 HD-2D 渲染管线"，并可独立成章成为第 7 章与第 8 章之间的新章节。

### 9.3.2 中期工作：可视化编辑器（数月）

中期目标是在引擎之上构建一个面向美术与策划的可视化编辑器。其总体设计可复用现有的 DebugUI 范式：

1. 在 Dear ImGui 之上扩展若干"工具窗口"——场景树、组件检视、资源浏览、日志输出；
2. 支持以拖拽方式向场景中放置实体、调整组件字段、保存为可由 Lua 加载的场景文件；
3. 引入"运行 / 暂停 / 单帧步进"等播放控制，使引擎在 Editor 模式下可冻结 PhysicSystem 与 CollisionSystem；
4. 对接 Tiled 等外部工具的导入流程，使 Editor 不必从零实现瓦片绘制；
5. 把 LuaBinder 中的字符串调度替换为基于组件元描述的自动绑定，使新增组件自动出现在编辑器中。

完成后，编辑器将作为新的第 8 章插入论文（原第 8 章性能测试相应顺延为第 9 章），主体结构保持稳定。

### 9.3.3 远期工作：AI 系统的深化与扩展

本课题已完成了 NPC AI 管线的核心实现（详见第 5.7 节）。在此基础之上，以下方向可作为后续演进：

1. **行为树（Behavior Tree）整合**：当前 DecisionSystem 采用 Utility AI 的单次决策模型，适合反应性行为；引入行为树可支持"巡逻 → 发现玩家 → 追击 → 失去目标 → 回归"等多阶段时序行为，两种机制可以互补共存（Utility AI 决策"做什么"，行为树管理"怎么做的步骤"）。
2. **目标导向行动规划（GOAP）**：将 ActionDef 的前置条件与效果形式化，引入规划器使 NPC 能根据当前世界状态自动生成动作序列，而无需手动为每种情境配置规则。
3. **可视化 AI 调试工具**：扩展现有 AIDebugUI，支持以图形化方式展示每个 NPC 的效用值柱状图、情绪曲线、知识事实列表，便于设计师在不看代码的情况下调优 NPC 人格参数。
4. **LLM 驱动的动态台词**：在 LineSystem 的"立场一致性"约束下，引入本地轻量语言模型（如 LLaMA 3 8B）为 NPC 生成未预设的即兴对话，使 HD-2D 风格的剧情在保持风格统一的同时具备更强的交互深度。

上述工作完成后可直接充实第 5.7 节或作为独立章节插入，不影响前序章节结构。

### 9.3.4 工程清理：与 Project_Audit 的对齐

除上述功能性扩展外，工程清理同样不可或缺。`docs/audit/Project_Audit.md` 已经按 P0–P3 的优先级列出了具体的修复清单，建议未来开发周期中以"每个迭代固定预留 20% 时间还工程债"的方式滚动清理。优先项包括：

- P0：`AudioSystem` 命名空间 `static` 全局改 `inline`；`RenderSystem` 中三个未加 `inline` 的 `Vector3` 全局；
- P0：以 `std::filesystem` 替代硬编码相对路径；
- P1：缓存 shader uniform location；
- P1：Lua `protected_function` 与错误恢复路径；
- P1：`CollisionSystem` 网格内存复用；
- P2：`SparseSet::emplace` 提供 `emplace_or_replace` 显式语义；`Registry::get` 提供 const 重载；
- P2：Lua 绑定的元描述化重构；
- P3：命名风格机械统一。

Project Rinn 当前阶段的工作至此告一段落。引擎以一个可读、可拆解、可演化的样本姿态站立在毕业设计的终点，也恰好站立在可继续生长为完整作品的起点。后续工作将按上文的分级路线继续推进，论文骨架已为它们留出位置。
