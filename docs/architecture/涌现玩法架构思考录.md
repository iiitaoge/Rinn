## ADR-001: Lua 与 C++ 的职责边界

### 元问题 (Why This Matters)

如果不定义边界，会出现两种极端：
1. **Lua 做太多**：性能崩溃，10000 实体遍历直接卡死
2. **C++ 做太多**：失去热更新能力，改一行逻辑要重新编译

### 失败方案

#### ❌ 方案 A: Lua 全权控制
```lua
function on_update(dt)
    for e in registry.view() do  -- 遍历 10000 实体
        local t = get_Transform(e)
        t.x = t.x + 1  -- Lua 每帧改位置
    end
end
```
**死因**：每次属性访问 20-50ns，10000 实体 × 60fps = CPU 爆炸

#### ❌ 方案 B: C++ 硬编码逻辑
```cpp
void PoisonSystem::Update() {
    for (auto e : view) {
        health.current -= 5;  // 数值写死
    }
}
```
**死因**：策划改数值要程序重编译，无法热更新

#### ❌ 方案 C: 命令队列模式
```
Lua → CommandQueue → C++ System
```
**死因**：过度设计，增加间接层，对于单机游戏没必要

### 胜出方案

**机制-策略分离 (Mechanism-Policy Separation)**

| 层 | 职责 | 频率 |
|---|---|---|
| C++ | 积分器：每帧维持物理状态 | 60fps × N |
| Lua | 脉冲：离散事件触发时设置参数 | 事件驱动 |

```lua
-- Lua: 只在按键瞬间调用一次
function on_key_down(key)
    if key == "W" then
        native.move(player, "up", 200)  -- 设置 Velocity
    end
end
-- 之后 C++ PhysicsSystem 每帧自动积分
```

### 设计原因

**频率-复杂度守恒**：高频操作必须在 C++，低频决策可以在 Lua。

## ADR-002: 组件能否包含动态内存

### 元问题

ECS 的性能优势来自于 **缓存命中率**。如果组件内有 `vector/map`，这个优势是否还在？

### 失败方案

#### ❌ 方案: 在组件内存关系
```cpp
struct SocialRelation {
    std::map<Entity, int> friendships;  // 堆分配！
};
```
**死因**：
1. 遍历时指针跳转 → Cache Miss
2. 无法 memcpy → 序列化复杂
3. 动态扩容 → 多线程不安全

### 胜出方案

**索引分离 (Index Separation)**

```cpp
// 组件只存索引或热缓存
struct Memory {
    Entity most_trusted;  // 只存最重要的
    int8_t trust_score;
};

// 完整数据在 System 管理的全局表
// RelationSystem::relations: vector<RelationEdge>
```

### 设计原因

**DOD 三铁律**：
1. 组件必须 POD (Plain Old Data)
2. 变长数据用 System 管理的 Pool
3. 组件只存定长热缓存

## ADR-003: 社会系统和经济系统如何统一

### 元问题

传统 RPG 有独立的"好感度系统"和"交易系统"。但它们是否是同一个东西的两面？

### 失败方案

#### ❌ 方案: 分离设计
```cpp
struct Wallet { int gold; };
struct Price { int base; float supply, demand; };
struct SocialRelation { int friendship, trust; };
struct Emotion { int mood, stress; };
```
**死因**：组件膨胀，且无法解释"为什么帮过我的人我更喜欢"

### 胜出方案

**价值统一理论 (Unified Value Theory)**

基于进化心理学：
- **朋友** = 历史上满足我 Needs 的人
- **敌人** = 历史上损害我 Needs 的人
- **价格** = 物品对我当前 Needs 的边际效用

```cpp
// 只需要 3 个组件
struct Needs { uint8_t hunger, energy, safety; };
struct Inventory { uint16_t items[8]; };
struct Memory { Opinion opinions[8]; };  // 对他人的评估

// 关系 = 交互历史经 Needs 评估后的积分
```

删除清单：Wallet, Price, Merchant, SocialRelation, Emotion

### 设计原因

**奥卡姆剃刀**：如果两个系统可以用同一套机制解释，就不要用两套。

## ADR-004: 感知系统的实现模式

### 元问题

AI 需要知道"谁在我视野里"。这个查询的复杂度如何控制？

### 失败方案

#### ❌ 方案 A: 拉模式 (每帧主动扫描)
```cpp
void AISystem::Update() {
    for (Entity ai : all_ais) {
        for (Entity other : all_entities) {  // O(N²)!
            if (InVisionCone(ai, other)) {
                // 看到了
            }
        }
    }
}
```
**死因**：O(N²) 复杂度，1000 实体 = 100 万次检查/帧

#### ❌ 方案 B: 仅空间划分
```cpp
// 用 SpatialGrid 减少检查范围
for (Entity other : grid.Query(ai.pos, vision_range)) {
    // 还是每帧每个 AI 都在查
}
```
**死因**：仍然是拉模式，只是常数优化，本质未变

### 胜出方案

**推模式 (事件驱动 + 空间划分)**

```cpp
// 事件发生时，主动广播
void ActionSystem::OnGunshot(Entity shooter, Vector2 pos) {
    Signal s { AUDIO, pos, intensity=100 };
    sensory_system.Emit(s);
}

// SensorySystem 被动接收
void SensorySystem::Update() {
    for (Signal s : signal_buffer) {
        for (Entity e : grid.Query(s.pos, s.intensity)) {
            if (CanPerceive(e, s)) {
                WriteToMemory(e, s.payload);
            }
        }
    }
    signal_buffer.clear();
}
```

**复杂度**：O(E × K)，E = 事件数，K = 局部实体数

### 设计原因

**物理真实性**：现实中，你不是每时每刻在扫描世界，而是等待刺激（信号）进入感官。

## ADR-005: 真理层与认知层分离

### 元问题

NPC 的知识应该是"客观事实"还是"主观认知"？GTA 警察为什么像开挂？

### 失败方案

#### ❌ 方案: 全局事实直接可读
```cpp
if (GlobalCrimeLog.Contains(player)) {
    police.Chase(player);  // 警察未亲眼看到，却知道是谁
}
```
**死因**：破坏沉浸感，NPC 像开挂

### 胜出方案

**三层认知模型 (Tripartite Cognition)**

| 层 | 内容 | 存储 | 特性 |
|---|---|---|---|
| 事实层 | 发生了什么 | 全局 EventLog | 客观、瞬时 |
| 传播层 | 信号如何传递 | 实时物理计算 | 有衰减、遮挡 |
| 认知层 | 谁知道什么 | 个体 Memory | 主观、持久 |

```
事件发生 → 发射信号 → 物理传播 → 感知过滤 → 写入记忆
```

**涌现效果**：
- 杀掉目击者 → 信息无法传递 → 完美犯罪
- 离得远 → 只听到声音 → 知道位置但不知道是谁

### 设计原因

**模拟物理而非模拟结果**：警察追人不是因为"知道谁犯罪"，而是因为"看到/听到了犯罪"。

## ADR-006: 社会关系的存储位置

### 元问题

"A 和 B 是朋友"这个信息存在哪里？A 的组件里？还是全局表里？

### 失败方案

#### ❌ 方案 A: 存在 A 的组件里
```cpp
struct SocialRelation {
    std::map<Entity, int> relations;
};
```
**死因**：违反 DOD，组件内有动态内存

#### ❌ 方案 B: 双向同步
```cpp
// A.relations[B] = 50
// B.relations[A] = 50  // 必须同步
```
**死因**：现实中关系是不对称的（A 认为 B 是朋友，B 可能不这么认为）

### 胜出方案

**主观记忆模型 (Subjective Memory)**

```cpp
// 每个人独立存储对他人的"印象分"
struct Memory {
    struct Opinion { Entity target; int8_t score; };
    Opinion opinions[8];  // 只存最重要的 8 个
};

// A 认为 B 是朋友 (A.opinions[B] = +50)
// B 可能认为 A 是路人 (B.opinions[A] = 0)
```

完整关系图在 `RelationSystem` 用 `vector<Edge>` 管理。

### 设计原因

**认知主观性**：关系不是客观连线，是每个大脑中对他人的价值评估缓存。

## ADR-007: 接口设计原则

### 元问题

Lua 应该调用 `set_Velocity(e, {vx, vy})` 还是 `move(e, "up", 200)`？

### 失败方案

#### ❌ 方案: 暴露组件
```lua
set_Velocity(player, {vx=100, vy=0})
set_Transform(player, {x=500, y=300})  -- 穿墙！
set_Health(player, {current=9999})      -- 无敌！
```
**死因**：Lua 可以绕过规则，破坏物理模拟

### 胜出方案

**暴露动作而非数据 (Expose Actions, Not Data)**

```lua
native.move(player, "up", 200)      -- 内部设置 Velocity
native.take_damage(player, 10)       -- 内部修改 Health + 触发检查
native.get_position(player)          -- 返回拷贝，只读
```

| 权限 | API 类型 | 示例 |
|---|---|---|
| 🟢 可执行 | 动作 | move, stop, attack |
| 🟡 只读 | 查询 | get_position, get_health |
| 🔴 禁止 | 直写组件 | set_Transform |

### 设计原因

**最小权限原则**：Lua 只知道"能做什么"，不知道"怎么实现"。
